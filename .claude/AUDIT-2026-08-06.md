## A. Modèle de montée en tier — le défaut central

### A1. Le jeu utilise des seuils pondérés ; le code utilise un ET booléen

**Le jeu** (`.claude/GAME_MECHANICS.md` §3, prouvé fichiers — `Residence7/UpgradeThreshold`) :
une maison monte d'un palier quand, **par catégorie de besoin**, la somme des `SupplyWeight` des
besoins **remplis** atteint le seuil. Le sous-ensemble est **au choix du joueur**.

Données réelles extraites (Patriciens) :

```
seuils   : Public 15 | Food 15 | Fashion 15 | Household 14 | Wonders 12 | Culture 8
services : Marché w1, Taverne w1, Sanctuaire w2, Grammaticus w2, Citerne w4,
           Théâtre w4, Maison de jeu w4, Temple w8, Bibliothèque w8   → Public, total 34
           Forum w4, Bains w4, Amphithéâtre w8                        → Wonders, total 16
```

Il faut donc **15 sur 34** en Public et **12 sur 16** en Wonders. Autrement dit :

- `Temple(8) + Bibliothèque(8) = 16 ≥ 15` → **2 bâtiments suffisent** pour Public ;
- `Amphithéâtre(8) + Forum(4) = 12` → **Bains devient inutile** (ou l'inverse) ;
- Food/Fashion/Household/Culture sont portés par des **biens**, tous satisfaits en mode import.

**Le code** — `planLattice.ts:498-506,523-525` et `packPlan.ts:305-313,326-328` :

```ts
const reqMask = chain.map((t) => { /* bit par service du tier */ });
// …
if ((reqMask[k] & coveredMask) === reqMask[k]) { ti = k; break; }
```

C'est un **ET sur les 12 services** du tier. Une maison doit être à distance-rue de **Marché ET
Taverne ET Sanctuaire ET Grammaticus ET Citerne ET Théâtre ET Maison de jeu ET Forum ET Bains ET
Temple ET Bibliothèque ET Amphithéâtre**. Le jeu n'exige rien de tel.

**Conséquence #1 — le mode `thresholds` est cassé par construction.** Ce mode choisit correctement
un sous-ensemble (mesuré : 9 services retenus, Temple et Bibliothèque écartés) puis le passe en
`serviceIds` aux moteurs. Mais `reqMask` est bâti sur `t.services`, c'est-à-dire les **12** services
du tier. Les bits de Temple et Bibliothèque ne sont donc **jamais allumés** — le commentaire de
`planLattice.ts:481-483` le dit explicitement et le présente comme une garantie anti-sur-comptage.
Résultat : `reqMask[Patriciens]` est insatisfiable, `reqMask[Equites]` aussi (Bains écarté), et
**tout plafonne à Plébéiens**. Mesuré : 0 maison au tier-cible, 1 793 maisons pour 7 180 habitants
contre 30 092 en mode `all`. Les deux moitiés du modèle se contredisent.

**Conséquence #2 — le mode `all` gaspille le sol.** Pour satisfaire le ET, le lattice doit blanketer
l'île de **tous** les types. Mesuré :

```
Amphithéâtre×1  Forum×7  Temple×7  Bains×7  Bibliothèque×8  Théâtre×12
Maison de jeu×20  Sanctuaire×14  Grammaticus×26  Marché×25  Taverne×30  Citerne×17
```

Soit ~14 100 tuiles de services — **30 % de l'île, plus que les maisons (26 %)**. Sous la règle
réelle, `Amphithéâtre + Forum + Temple + Bibliothèque` suffisent : ~5 000 tuiles, et ce sont
justement les portées les plus longues (street 250/70/68/62), donc les plus faciles à couvrir.

### A2. La capacité/maison est traitée comme une constante par tier

**Le jeu** : `capacité = Σ Population des NeedAttributes des besoins REMPLIS`. C'est exactement ce que
calcule `tools/build_economy.py:246,258` (`capacity += attrs.get("Population", 0)` sur biens **et**
services). Mesuré sur Patriciens : `cap=35` tous besoins remplis, `cap=17` avec le sous-ensemble seuils.

**Le code** : `islandPlan.ts:133-139` retourne `t.capacityDefault` (constante) ou le `cap` global du
profil seuils. Une maison couverte par 11 services sur 12 est comptée exactement comme une maison
couverte par 4 — elle chute d'un palier entier ou reste au maximum. L'objectif d'optimisation est en
**marches d'escalier**, ce qui prive le glouton et le recuit de tout gradient exploitable.

### Correctif A — modèle « besoins remplis par maison »

Remplacer le masque booléen par un **accumulateur pondéré par catégorie**, calculé par maison :

```ts
// par maison, à partir des services qui la couvrent réellement (+ biens, tous remplis en import)
type NeedScore = Record<string, number>;              // catégorie → Σ SupplyWeight remplis

function houseTier(chain: Tier[], covering: Set<string>, goodsMet: boolean): { tier: Tier; cap: number } {
  for (let k = chain.length - 1; k >= 0; k--) {
    const t = chain[k];
    const score: NeedScore = {};
    let cap = 0;
    for (const g of t.goods) if (goodsMet) { score[g.category] = (score[g.category] ?? 0) + g.weight; cap += g.pop; }
    for (const s of t.services) if (s.building && covering.has(s.building)) {
      score[s.category] = (score[s.category] ?? 0) + s.weight; cap += s.pop;
    }
    if (Object.entries(t.upgradeThresholds).every(([c, target]) => (score[c] ?? 0) >= target)) {
      return { tier: t, cap: Math.max(1, Math.round(cap)) };
    }
  }
  return { tier: chain[0], cap: chain[0].capacityDefault };
}
```

Trois gains simultanés :

1. **Réalisme** — c'est la mécanique du jeu, prouvée fichiers, plus une approximation.
2. **Flexibilité** — le solveur n'a plus à poser 12 types ; il peut arbitrer *Temple+Bibliothèque*
   (2 gros, portée 68/62) contre *Citerne+Théâtre+MJeu+Sanctuaire+Grammaticus* (5 petits), selon la
   forme de l'île. C'est exactement le levier « le plus flexible » demandé.
3. **Optimisabilité** — l'objectif devient `Σ_maisons cap(maison)`, continu et croissant : chaque
   service supplémentaire couvrant une maison ajoute son `pop`. Le glouton min-cover peut enfin
   raisonner en gain marginal réel plutôt qu'en franchissement de seuil.

Ce correctif rend le mode `thresholds` inutile : la sélection du sous-ensemble devient une
**conséquence** de l'optimisation spatiale, pas un pré-choix global par ratio coût/poids.

**Estimation de gain.** Libérer ~9 000 tuiles de services → ~1 000 emplacements 3×3 supplémentaires,
et un taux au tier-cible bien supérieur à 52 % (4 services à longue portée sont bien plus faciles à
blanketer que 12). Ordre de grandeur attendu : **×2 à ×3 sur les habitants**, à valider par mesure.

**Points de modification** : `planLattice.ts` (`reqMask`/`placeHouses`), `packPlan.ts` (finalisation),
`islandPlan.ts` (`capForTier`/`mixedResidents`/gate eau), `economy.ts` (`residentialChain`).
Les snapshots de régression `planLattice.test.ts` devront être régénérés — c'est attendu.

## B. Sélection de moteur (portfolio) — biais mesuré en faveur de packPlan

`islandPlan.ts:126-149` lance les deux moteurs et garde le meilleur `mixedResidents`. Mais
**planLattice route l'eau** (`water: true`) et exclut de son comptage les services non raccordés
(`planLattice.ts:496`), tandis que **packPlan ne route rien** et suppose tous les services actifs
(commentaire assumé, `packPlan.ts:296-297`). Les deux candidats sont donc comparés sur des échelles
différentes : l'un pénalisé par la réalité de l'eau, l'autre non.

Mesuré en mode `thresholds` :

```
A lattice (eau-aware) : maisons=1793  mixte=7180
B packPlan (sans eau) : maisons=2294  mixte=7189   ← gagne de 9 habitants (0,1 %)
```

packPlan l'emporte pour **9 habitants**, puis `islandPlan` route l'eau *a posteriori* sur une île
déjà saturée de maisons : **2/40 consommateurs raccordés** au lieu de 30/30 que le lattice atteignait.
Le gate eau démote alors tout le monde. Le plan livré est très inférieur au plan écarté.

C'est un cas d'école de **critère de sélection ≠ métrique livrée**.

**Correctif B.**
1. Évaluer chaque candidat **après** application du gate eau — extraire la démotion de
   `islandPlan.ts:186-201` en fonction pure `applyWaterGate(cand, water)` et l'appliquer aux deux
   candidats avant `better()`.
2. Rendre packPlan eau-aware (router l'eau avant la phase maisons, comme le lattice), ou l'exclure
   du portfolio dès que le tier comporte un consommateur d'eau. C'est le cas de tous les tiers ≥ 3.
3. Départager les quasi-ex æquo (< 2 %) sur un critère robuste — taux de raccordement d'eau, puis
   nombre de services — au lieu du hasard numérique.

**Effort : S.** C'est le meilleur ratio impact/effort de tout l'audit.

## C. Réseau routier — 24 % de l'île

`planLattice.ts:88-89` :

```ts
const STEPH = 2 * rh + 1;                                  // 7 pour une résidence 3×3
const STEPV = Math.max(rw + 2, Math.min(2 * rw + 1, 11));  // 7
```

Peigne horizontal tous les 7 + épines verticales tous les 7. Mesuré : 11 297 tuiles de route après
élagage, soit **24 %** de la terre — contre 26 % pour les maisons.

Le pas horizontal est correct : 7 = 1 route + 2 rangées de maisons 3×3 (optimal en 4-adjacence).
**Les épines tous les 7 colonnes sont le gaspillage** : elles servent la connexité et raccourcissent
la distance-rue, mais 1 colonne sur 7 coûte ~12 % du sol à elle seule.

**Correctif C.**
1. **Espacer les épines** (14–21 au lieu de 7) et mesurer l'effet réel sur la distance-rue. La marge
   est confortable : les grands services ont une portée de 62–70, un détour de 10–20 tuiles reste
   absorbable. Gain attendu : **6–9 % de sol**, soit ~700–1 000 maisons.
2. **Rendre l'espacement adaptatif** : le dériver de `min(range)` des services *effectivement retenus*
   (après correctif A, ce sont les grands) plutôt que d'une constante figée à 11.
3. **Exploiter la 8-adjacence** déjà implémentée sur la grille ½-tuile (`rules.ts:27`) : une route
   diagonale relie deux bandes en coupant les coins. Aujourd'hui les moteurs tournent en tuiles
   4-adjacentes et n'en profitent jamais. ⚠ dépend de `[OUVERT in-game #3]` (§13 GAME_MECHANICS) —
   à tester en jeu avant d'y investir.
4. L'élagage final (`pruneRoads`) ne garde que les chemins maison→service ; il pourrait aussi
   **fusionner les segments redondants** entre deux services voisins.

## D. Eau et aqueducs

### D1. Constantes non calibrées
`waterPlan.ts:19,24` : `MAX_RUN = 140` et `CLIMB_MARGIN_Q = 2` sont des valeurs qualitatives,
signalées comme telles dans le code. Elles décident pourtant du raccordement de **tous** les services
T3+, donc du tier atteignable. Les tests in-game #1 et #2 de GAME_MECHANICS §13 les calibreraient en
une session de jeu. **C'est le meilleur retour sur investissement hors code.**

### D2. `blockMountains` est un pifomètre coûteux
`waterPlan.ts:31` : `MOUNTAIN_BLOCK_RADIUS = 6` → 13×13 = 169 tuiles bloquées par slot. Sur cette
île (12 slots) : jusqu'à **2 028 tuiles, 4,3 % du sol**, retirées sur une constante arbitraire.
**Correctif** : la heightmap est déjà extraite (`terrain.ts:50`, `hasHeights`) — dériver la zone
inconstructible de la **pente réelle** (`SteepnessMaxHeightDiff`, GAME_MECHANICS §7) au lieu d'un
disque de Chebyshev. Bénéfice double : sol récupéré et constructibilité correcte partout.

### D3. Les slots montagne sont une ressource partagée non arbitrée
Mesuré : le mode population consomme **8 des 12 slots** en sources d'aqueduc. Le mode production
(`prodPlan.ts:162-193`) pose ses **mines** sur ces mêmes slots. Aucun des deux ne sait ce que
l'autre consomme, et `multiIslandPlan` ne les arbitre pas non plus.
**Correctif** : faire du budget de slots une contrainte explicite de la requête de plan
(`slotsReserved`), et l'exposer dans l'UI (« 8/12 slots utilisés par l'eau »).

### D4. La règle NO-MERGE est bien modélisée
`waterPlan.ts:344-346,353-355` : une conduite ne traverse jamais un réseau existant, seule
l'arrivée peut être une jonction. Conforme à `[IN-GAME]` GAME_MECHANICS §4. Le BFS à états
(case × direction d'entrée) pour le franchissement de route en ligne droite est correct et élégant.
**Rien à corriger.**

## E. Bâtiments manquants du modèle

### E1. Aucun comptoir/port en mode import — le plan est injouable
`grep roadRoot src/optimizer/` ne renvoie que `greedy.ts` (qui se contente de *raccorder* un comptoir
verrouillé existant). Ni `planLattice`, ni `packPlan`, ni `planIslandImport` ne posent de
`HarborWarehouse`/`TradeBuilding`.

C'est contradictoire avec l'archetype lui-même : une **île d'import** reçoit ses 27 biens **par le
port**. Sans comptoir, rien ne débarque et le réseau routier n'a pas de racine. Le bug est invisible
car `rules.ts:104` renvoie `hasRoot: false` et valide alors *toutes* les routes — l'éditeur affiche
donc un plan tout vert.

**Correctif E1.** Poser un comptoir en phase 0 : chercher une case côtière (`grid.water` est déjà
disponible), y ancrer le réseau, puis vérifier `rootedRoadSet(...).hasRoot === true` dans le contrat
de sortie du planner. Le mode production le fait déjà pour ses entrepôts (`prodPlan.ts:105`) — il n'y
a qu'à généraliser. **Effort : S.**

### E2. Institutions anti-incidents absentes
Vigiles (street 30), Medicus (38), Préfecture (34) sont dans le catalogue mais ne sont **jamais
posés** : ils ne figurent pas dans `tier.services` (ce ne sont pas des besoins). Or GAME_MECHANICS
§10 documente une propagation du feu par sauts euclidiens avec `BurstDistance 25 / BurstCount 6` sur
les **mines**. Une île de production réelle brûle.
**Correctif** : couche de placement optionnelle post-plan, min-cover en distance-rue sur les
bâtiments à `HeatValue`, avec une case à cocher « protection incidents » dans l'UI.

### E3. Ornements, parcs, coût de construction
Aucun ornement n'est placé, et **le coût de construction n'est calculé nulle part** — ni argent, ni
matériaux, alors que `Upgradable/PossibleUpgrades` porte des `Cost` (GAME_MECHANICS §3) et que les
routes ont un coût connu (terre 5, pavée 40, §1). Un plan qui annonce « +41 904/min » sans dire
« coûte N crédits + M briques à bâtir » est incomplet pour décider.
**Correctif** : sommer `Cost` par bâtiment posé + coût des routes, et l'afficher en tête de résultat.

## F. Extraction de données (`tools/`)

Globalement le point fort du projet : extracteur RDA écrit from scratch, correction `BuildBlocker`
(audit 2026-06), garde-fous sur les overrides périmés (`build_economy.py:290-294`). Trois réserves :

### F1. Le masque terre/mer vient d'un PNG de rendu
`build_islands.py:43-49` : seuillage `somme RGB > 120` sur `mapimage.png`, puis `Image.BOX` vers la
taille réelle. C'est un **rendu**, pas une donnée de simulation : plages, falaises et zones sombres
sont classées au petit bonheur, et le redimensionnement d'un masque binaire crée de l'aliasing sur
tout le littoral.

Or la heightmap **est déjà extraite** et documentée : `med01_gamedata.data → TerrainManager/HeightMap`,
641×641 int16, mer < 0 / terre > 0 (GAME_MECHANICS §7, validé). Le critère `h > 0` est la vérité
terrain du jeu.
**Correctif** : dériver `usable` de la heightmap dans `build_terrain.py` et n'utiliser `mapimage.png`
que comme vignette d'aperçu. Impact direct sur la fidélité de **toutes** les îles.

### F2. 63 bâtiments sur 343 restent à la taille par défaut 3×3
`build_catalog.py:357` : `size = b.get("size") or {"w": 3, "h": 3}`. Le repli est **silencieux** —
rien ne distingue « vraiment 3×3 » de « `.ifo` introuvable ».
**Correctif** : marquer `sizeSource: "buildblocker" | "extents" | "default"` dans le catalogue,
l'afficher dans l'éditeur de catalogue, et faire échouer le build si un bâtiment **utilisé par les
planners** tombe sur le défaut.

### F3. La région est déduite d'une sous-chaîne
`build_economy.py:220-221` (`"roman" in name.lower()`), et côté app
`islandId.includes("celtic")` — répété dans `prodPlan.ts:69`, `multiIslandPlan.ts:42`,
`IslandPlanner.tsx:53`. Un renommage d'asset côté Ubisoft casse silencieusement la sélection de
producteur. `AssociatedRegions` est déjà lu par `build_catalog.py:178` : le propager.

## G. Économie et solveur

### G1. Le solveur est solide
Point fixe population→besoins→production→main-d'œuvre avec détection de divergence et repli sur les
besoins directs (`solve.ts:284-293`), mémoïsation de l'entretien par unité, préférence régionale de
producteur, comptabilisation des imports et de leur coût. La convergence tient à
`NeedConsumptionRate` par **maison** — hypothèse [WEB], point de bascule déjà câblé
(`consumptionUnit`, `solve.ts:207`) en attente du test in-game #4. Bonne ingénierie.

### G2. `DEFAULT_HOUSES_PER_SERVICE = 30` est une constante magique
`solve.ts:4` : « un bâtiment de service couvre 30 maisons ». C'est faux et surtout inutile — le
planner **connaît** la couverture réelle, elle est calculée par BFS distance-rue. Cette constante
fausse `serviceCounts`, donc l'entretien, donc le net affiché.
**Correctif** : quand un plan spatial existe, injecter les comptes de services **réels**
(`servicesPlaced`) au lieu de l'estimation. `solve` garde la constante pour l'usage hors-plan.

### G3. `residentialChain` repose sur une inclusion d'ensembles fragile
`economy.ts:85-96` : la chaîne est reconstituée par « même région + capacité ≤ + services ⊆ ». Sur
les données actuelles cela donne le bon résultat (Liberti ⊂ Plébéiens ⊂ Equites ⊂ Patriciens, et
Mercators/Nobles correctement exclus car ils exigent Fanum/Théâtre bardique). Mais c'est une
**inférence**, alors que la donnée existe : `Upgradable/PossibleUpgrades` décrit la vraie chaîne de
progression (GAME_MECHANICS §3).
**Correctif** : extraire `PossibleUpgrades` dans `build_economy.py` et construire la chaîne dessus.

### G4. `importCost` utilise `BasePrice` comme prix d'achat
`solve.ts:348`. Approximation assumée dans le code. À revalider si les prix PNJ diffèrent
(GAME_MECHANICS §8, `[OUVERT]`).

## H. Multi-îles

`multiIslandPlan.ts` est explicitement un v1. Trois limites structurelles :

1. **Aucun tonnage.** Un bien est assigné à une île si elle *peut* le produire (`canProduce`), sans
   vérifier qu'elle en a la **place**. Une petite île peut se voir attribuer 8 chaînes.
2. **Seul le bien primaire est planifié** (`multiIslandPlan.ts:114-121`) : les 7 autres sont annoncés
   mais jamais placés. Le « covered: true » du bilan est donc trompeur.
3. **Heuristique « la plus petite île d'abord »** (ligne 94) sans notion de capacité — l'inverse de
   ce qu'il faut quand la chaîne est lourde.

**Correctif H.** Passer à une boucle de **dimensionnement itératif** : estimer le sol requis par
chaîne (via `solve` → nombre de bâtiments × emprise + champs), assigner par *first-fit decreasing*
sur le sol disponible, puis planifier **toutes** les chaînes d'une île en un seul appel `prodPlan`
avec une demande multi-biens (`extraDemand` accepte déjà un vecteur). Réutiliser la contrainte de
slots montagne de §D3.

## I. Interface

### I1. Le résultat de plan est du texte, sans carte
`IslandPlanner.tsx:171-235` : le seul retour visuel est « Placer sur l'île → », qui écrase le layout
courant. L'utilisateur ne peut pas voir **où** sont les Liberti et **pourquoi**. Sur le plan mesuré,
493 maisons sont bloquées au palier de base — sans carte, impossible de savoir si c'est la bordure,
un trou d'eau, ou une zone hors de portée du Temple.
**Correctif** : miniature de prévisualisation dans le panneau résultat, colorée **par tier atteint**,
avec un survol qui liste les besoins manquants de la maison pointée. C'est le principal levier
d'utilisabilité du produit.

### I2. Le mode `thresholds` est proposé alors qu'il est cassé
Le sélecteur « Seuils d'upgrade (min services → + de maisons) » (`IslandPlanner.tsx:133-136`) promet
plus de maisons et livre 0 % au tier-cible (§A1). À masquer tant que le correctif A n'est pas fait.

### I3. `feasible: false` n'est presque jamais expliqué
`islandPlan.ts:277` : `feasible = houses > 0 && fullyCoveredPct >= floor`. Les deux plans mesurés
sont `false`, et l'UI affiche seulement « (best-effort) ». Les `gaps` existent et sont bons —
les remonter en tête, pas en queue.

### I4. Détails
- `IslandPlanner` reçoit `asView` marqué « conservé pour compat » (`IslandPlanner.tsx:13`) mais

- `placeMsg` est déclaré (ligne 45), affiché (ligne 234), **jamais assigné** à autre chose que `null`.
- Aucun moyen de comparer deux exécutions ni de figer un plan pour itérer dessus.

## J. Architecture, performance, tests

### J1. Deux systèmes d'optimisation parallèles
`greedy.ts` + `anneal.ts` + `score.ts` (recuit simulé sur étagères, piloté par `OptimizerPanel`)
d'un côté ; `planLattice`/`packPlan`/`islandPlan` de l'autre. Le premier n'est plus utilisé que
comme sous-routine de `prodPlan.ts:112`. `score.ts` porte une fonction objectif
(count/coverage/compact/roads) qui ne sert plus à rien pour le plan d'île.
**Correctif** : assumer le recuit comme *back-end de placement de masse pour la production* et le

### J2. Performance : correcte, pas un sujet
1,3 s pour une île 320×320. Les optimisations en place (greedy incrémental, tables de sommes

### J3. Tests : 167 verts, 31 fichiers, mais un angle mort
La couverture est bonne (géométrie, règles, score, économie, snapshots de régression déterministes).

*actuel* (golden snapshots), pas le comportement *correct* — c'est précisément pourquoi §A1 a pu
survivre.
**Correctif** : une suite `gameRules.test.ts` dérivée directement des seuils de
`economy.generated.json`, indépendante des moteurs.

### J4. `.claude/ROADMAP.md` est périmé
Il annonce « 124 tests, branche feature/operational-polish » ; l'état réel est 167 tests sur `dev`,
toutes les branches feature étant fusionnées dans `main`. À réécrire à partir du présent audit.
